# 2026-10-13 [bsj] 원문 대기와 경과 시간 수정

## 확인한 원인과 변경

사진의 ‘가져온 원문 · 62초’는 원문 읽기에만 걸린 시간이 아니라 의도 분석·추출·검색부터 합산한 요청 누적 시간이었습니다. 해당 숫자만으로 읽기 노드가 62초 걸렸다고 단정할 수 없습니다. 완료 상태에서는 저장된 전체 시간을 표시하지 않고 마지막 단계의 타이머를 사용하여, 마지막 단계가 짧으면 0초로 표시되었습니다.

최근 변경은 일반 검색 이후 주장별 YouTube 검색을 추가 모델 요청으로 기다리게 했습니다. 또 YouTube 자막 스레드는 대기·HTTP 요청 시간 제한이 없었습니다. 이것이 특정 사진의 62초를 전부 설명한다는 실측 근거는 없지만, 원문 표시를 지연시킬 수 있는 코드 경로는 확인했습니다.

| 항목 | 변경 전 | 변경 후 |
|---|---|---|
| LLM 검색 호출 | 일반 검색 1회 + 고유 주장 검색어별 YouTube 모델 요청(최대 3회) | 이전처럼 모델 요청 1회에 일반·YouTube 검색어와 검색 지침 포함 |
| Tavily 검색 | 일반 검색 뒤 YouTube 검색을 기다림 | 일반·YouTube 검색을 동시에 시작하며, 실패·취소 시 미완료 요청 정리 |
| YouTube 읽기 | 자막 대기로 출처 수집이 길어질 수 있음 | 출처별 전체 조회 8초 제한, 자막 스레드 대기·HTTP에도 제한 적용 |
| 원문 시간 | 요청 시작부터 원문 도착까지 누적 시간 | 읽기 단계 시작 이벤트부터 원문 도착까지의 시간 |
| 상단 경과 시간 | 단계 변경 시 초기화, 완료 시 마지막 단계 시간 | 요청 전체 시간을 이어서 표시하고 완료·오류·취소 시 고정 |

영상 검색 지침·Tavily 도메인 제한·출처 6개 한도·관련 영상 자리 확보와 기존 주장별 출처 강조는 유지했습니다. 최신 `origin/main`의 `e2183d5`를 `feat/frontend`에 fast-forward한 뒤 수정했습니다.

빌드가 생성한 `next-env.d.ts` 경로 변경은 제외했습니다. 검증용 웹·백엔드 서버를 추가로 실행하지 않았습니다.

## 남은 확인

- 사진과 같은 질문을 실제 공급자로 다시 실행하여 전체 62초가 몇 초로 줄어드는지 측정하지 않았습니다. 검색 지연·의도 분류·판정 지연은 모델과 입력에 따라 달라집니다.
- 화면의 전체 시간과 단계별 시간은 브라우저가 이벤트를 받은 시점을 기준으로 계산하므로 서버 내부의 순수 실행 시간과는 차이가 있을 수 있습니다.
- 실제 브라우저 시각 확인·공개 배포 반영은 아직 확인하지 않았습니다.
