# 의도 분류 인증 오류 디버그 (2026-10-12)

## 요약

반복 분류 실패의 원인은 Hive 인증 거절입니다. 사용자 키 갱신 뒤에도 이전 프로세스 환경변수가 파일 값을 덮었습니다. 상속을 제외하여 실제 분류를 복구하고, 인증·기술 오류를 사용자 의도 모호함으로 안내하던 문제도 수정했습니다.

## 원인·수정

- `2024년 한국 합계출산율은 0.75명이다.`와 명시적 DeepSeek 선택으로 프론트 503(0.31초), 백엔드 502(0.28초)를 재현했습니다. 일회성 메모리 진단의 실제 Hive 응답은 `401 Invalid or expired token`입니다. 대화·이미지는 전송하지 않고 인증 헤더·키는 출력하지 않았습니다.
- 실행 서버의 `/health`는 당시 HEAD `c20ef06`과 일치했으며 요청 계약도 최신입니다. 구버전 서버·의도 판단 시간 초과를 원인으로 보지 않습니다.
- [Hive 공식 문서](https://docs.thehive.ai/docs/chat-completions-openai-compatible-llms)의 V3 URL·`Bearer` 방식과 코드가 일치합니다. V3 Service API Keys의 Secret Key를 사용해야 하며, 현재 인증 거절의 세부 이유는 키 만료·다른 종류·폐기 등을 구분할 수 없습니다.
- 사용자 갱신 완료 후에도 401이 재현됐습니다. 키값·길이·해시를 출력하지 않는 메모리 진단에서 프로세스 환경변수의 존재를 확인하고, Bearer 중복·공백·외곽 따옴표는 배제했습니다. 이 환경변수만 제외한 새 프로세스의 실제 분류가 200·`verify/current`(1.16초)로 통과하여 이전 환경변수 우선 적용을 확인했습니다.
- 401·403을 인증 예외로 구분하고 기존 HTTP 오류를 원인으로 보존합니다. 의도 분류·백엔드·프록시가 안전한 `PROVIDER_AUTH_FAILED`만 전달합니다. 공급자 원문·비밀값을 응답에 포함하지 않습니다.
- 화면은 인증·접근 권한 문제를 표시하고, 일반 기술 실패도 확인 질문과 구분합니다. 원격 `d87d0c2`의 명시적 검증 요청 폴백은 보존하고 인증 거절 때만 차단합니다. 명시적 모델 자동 우회는 추가하지 않았으며 Auto 폴백·동의·취소·정상 확인 질문은 유지합니다.

## 브라우저·서버

- 시험 백엔드 8017·production 프론트 3017에서 Chrome으로 확인했습니다. 외부 모델·실제 DB 없이 실제 프록시·UI를 사용했습니다. 병합 전 동일 통계 문장 2회·일반 오류·정상 확인 질문에서 intent 4회·검증 0회를 확인했습니다.
- 병합 후 DeepSeek를 선택하여 통계 문장·명시적 검증 요청의 인증 거절을 확인했고 두 경우 모두 검증 0회였습니다. 일반 장애의 명시적 요청은 검증 1회로 이어지고, 실제 `clarify`는 확인 질문으로 표시됩니다. 최종 intent 4회·검증 1회입니다. [인증 안내 검증 화면](2026-10-12-의도분류인증.png)을 저장했습니다.
- 시험 서버·탭 종료 및 3017·8017 포트 폐쇄를 확인했습니다. 사용자 3000 개발 프론트·8010 백엔드는 같은 모드로 재시작하여 유지합니다.
- 최초 재시작 후 같은 입력은 503 `PROVIDER_AUTH_FAILED`(0.36초)로 새 오류 전달을 확인했습니다. 사용자 키 갱신 및 이전 `HIVE_API_KEY` 상속 제외 후 백엔드를 다시 시작했습니다. 같은 입력의 사용자 프록시 `POST http://127.0.0.1:3000/api/intent`는 실제 Hive를 통해 200·`action=verify`·`target=current`(1.09초)로 통과했습니다. 코드 커밋·푸시 후 재시작한 서버에서도 200·`verify/current`(1.38초)를 확인했습니다. 이 시간은 의도 분류만 측정한 값입니다. 사용자 3000·8010 포트만 열려 있고 작업 트리는 깨끗했습니다.

## 남은 범위

- 실제 검증 전체의 정확도·지연·공개 배포는 이번 분류 정상화 및 모의 회귀와 구분합니다. 정상적인 환경변수 우선 정책은 변경하지 않았습니다. 향후 로컬 실행에서도 이전 `HIVE_API_KEY` 프로세스 환경변수가 파일의 새 키를 덮지 않도록 관리해야 합니다. 이번 제외는 실행한 백엔드 프로세스에만 적용했습니다.
- 환경 파일은 직접 열거나 수정하지 않았습니다. 기존 `feat/agent`에서 진행하며 별도 브랜치·원격 배포·다른 모델로의 강제 전환은 하지 않았습니다.
