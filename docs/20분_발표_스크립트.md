## 발표 전 준비

- [시스템 구성도](diagrams/system-architecture.svg)와 [검증 아키텍처 구성도](diagrams/workflow-architecture.svg)를 발표 화면에 미리 띄웁니다.
- 시연 질문은 발표 전에 실제로 실행해 판정과 출처가 잘 표시되는지 확인하고 고정합니다.
- 시연이 오래 걸릴 때를 대비해 결과 화면을 준비합니다. 준비한 예시 화면은 실제 실시간 검증 결과처럼 소개하지 않습니다.
- 모델 키나 DB 연결 정보가 화면·터미널에 보이지 않는지 확인합니다.

## 발표 스크립트

### 0:00–1:30 | 인사와 프로젝트 소개

안녕하세요. 저희 팀 프로젝트 **True or Not**을 소개하겠습니다.

인터넷에는 뉴스 기사, SNS 게시물, 댓글처럼 확인이 필요한 정보가 많이 올라옵니다. 한 문장 안에도 확인 가능한 사실과 작성자의 의견, 아직 확정되지 않은 예측이 섞여 있을 수 있습니다. 검색 결과만 몇 개 보는 것으로는 그 주장이 실제 자료와 맞는지, 자료의 조건이 같은지 판단하기 어려울 때가 많습니다.

True or Not은 사용자가 가져온 주장을 원문 자료와 비교하고, 확인된 내용과 불확실한 내용을 출처와 함께 보여주는 웹 서비스입니다. 서비스 이름은 참과 거짓을 확인한다는 뜻이지만, 결과를 무조건 둘 중 하나로 단정하지는 않습니다. 근거가 충분하지 않으면 그 한계를 함께 설명하는 것이 프로젝트의 핵심입니다.

오늘은 먼저 서비스와 시스템 구성을 설명하고, 검증 흐름을 살펴본 뒤 실제 화면에서 입력부터 결과 확인까지 시연하겠습니다. 마지막으로 개발·배포 환경과 현재 자동 검증의 범위를 말씀드리겠습니다.

발표를 들으실 때는 결과의 색이나 참·거짓 표시만 보시기보다, 각 판정에 어떤 원문이 연결되어 있는지 같이 봐주시면 좋겠습니다. 저희가 만들고자 한 것은 답을 대신 정해주는 도구가 아니라, 사용자가 근거를 직접 확인하는 과정을 돕는 도구이기 때문입니다.

### 1:30–3:00 | 문제와 사용자 필요

이 프로젝트가 해결하려는 문제는 온라인에서 본 주장의 출처와 조건을 사용자가 쉽게 따라가기 어렵다는 점입니다.

예를 들어 “가격이 올랐다”는 문장이 있어도 어떤 상품인지, 어느 기간인지, 가격을 어떤 단위로 비교했는지에 따라 의미가 달라집니다. 정책 관련 글도 확정된 내용인지 검토 중인 내용인지, 발표 시점과 시행 시점이 같은지 확인해야 합니다. 또 검색 결과에 비슷한 기사가 여러 개 보여도 모두 같은 보도자료를 인용했다면 독립적인 근거 여러 개라고 보기 어렵습니다.

사용자가 원하는 것은 모델이 정답을 단정하는 것만이 아닙니다. 어떤 주장 부분을 확인했는지, 그 판단을 뒷받침하는 원문이 어디인지, 확인하지 못한 조건은 무엇인지 알고 싶어 합니다.

그래서 저희는 검색된 문장이나 AI가 만든 설명을 원문 인용처럼 보여주지 않도록 하고, 접근해 읽은 자료와 실제 인용을 연결하는 데 중점을 뒀습니다.

예를 들어 검색 결과 제목에 “연구 결과 확인”이라고 적혀 있어도, 실제 본문을 열어보면 다른 연구를 소개하는 기사일 수 있습니다. 또 본문에서 한 문장만 떼어오면 앞뒤 조건이 빠져 원래 의미와 달라질 수도 있습니다. 검색 결과를 모으는 것과 주장을 검증하는 것을 같은 단계로 취급하지 않는 이유입니다.

사용자가 링크를 넣었을 때도 링크가 있다는 이유만으로 그 내용을 모두 읽었다고 가정하지 않습니다. 페이지 접근 여부와 가져온 원문의 범위를 확인하고, 확인할 수 없는 정보가 있다면 그 한계를 결과에 남기는 방식으로 설계했습니다.

### 3:00–4:30 | 제품 목표와 원칙

사용자는 텍스트나 링크를 입력하고 확인 요청을 보냅니다. 서비스는 입력에서 확인할 주장을 나누고, 관련 출처와 원문을 찾아 주장을 대조합니다. 결과에는 판정, 근거 인용, 출처 링크와 확인 과정의 경고가 표시됩니다.

제품은 검색 결과가 없다는 이유만으로 주장을 거짓이라고 하지 않습니다. 직접 확인할 자료가 충분하지 않으면 근거 부족으로 안내하고, 의견이나 미래 예측은 현재 확인된 사실처럼 판정하지 않습니다. 검색 자료에 접근할 수 없을 때도 접근 불가 상태를 표시하고, 로그인이나 유료벽을 우회하지 않습니다.

또한 사용자의 내용이 외부 서비스로 전송되기 전에 동의를 확인합니다. 외부 전송 동의와 대화 저장 동의는 별개입니다. 검증을 사용했다고 해서 대화가 자동으로 저장되지는 않습니다.

이러한 원칙은 결과를 더 그럴듯하게 보이게 하는 것보다, 사용자가 확인 범위와 한계를 이해하도록 하는 데 목적이 있습니다.

저희가 특히 구분하려는 것은 ‘틀렸음’과 ‘아직 확인하지 못함’입니다. 관련 자료를 찾지 못했다는 사실만으로 주장이 거짓이라고 결론 내릴 수는 없습니다. 반대로 출처가 하나 있다는 이유만으로 주장을 참이라고 확정할 수도 없습니다. 그래서 판정에는 확인된 원문과 남은 불확실성을 함께 반영합니다.

또한 서비스가 다루는 범위도 정해두었습니다. 입력한 사실 주장의 근거 확인이 중심이며, 사용자의 의견이나 미래 예측을 사실 판정처럼 다루지 않습니다. 의료·법률·투자 판단이나 작성자 평가처럼 별도 전문성이 필요한 영역을 대신 판단하는 서비스도 아닙니다.

### 4:30–6:30 | 시스템 구성도

화면의 시스템 구성도를 보시면 전체가 네 영역으로 나뉘어 있습니다. 왼쪽은 Frontend, 가운데는 Backend, 다음은 Data, 오른쪽은 외부 서비스입니다.

Frontend는 Next.js로 만든 웹 화면과 서버 프록시입니다. 사용자는 브라우저에서 질문을 입력하고 검증 진행 상황과 결과를 확인합니다. 프론트엔드는 Vercel에 배포되어 있습니다. 브라우저가 백엔드에 직접 비밀 키를 보내지 않도록 요청은 Next.js 서버 프록시를 거칩니다.

Backend는 FastAPI와 LangGraph로 구성했습니다. FastAPI가 요청을 받고, LangGraph가 검증 단계를 진행합니다. 검색, 원문 수집, 모델 판정, 대화 저장 기능도 백엔드에서 연결합니다.

Data 영역에는 검증 중에 사용되는 주장·출처·근거 상태와 화면으로 전달할 결과, 그리고 동의한 대화를 보관하는 PostgreSQL이 있습니다. 검증 처리 중 상태와 영구 저장 데이터는 용도가 다르기 때문에 그림에서도 구분했습니다.

오른쪽 외부 서비스에는 검색 도구, 웹 원문, 모델 공급자가 있습니다. Auto 설정에서는 DeepSeek V4.1 Flash MAX, GPT-6 Luna, Gemini 모델을 순서대로 시도하며, DeepSeek는 Hive API를 사용합니다. 외부 공급자 연결이 실제로 성공하는지는 오프라인 CI 통과만으로 판단하지 않고 별도의 QA 기록으로 확인합니다.

요청이 화면에서 백엔드로 이동하는 경로도 보시면 좋습니다. 브라우저는 Next.js 서버 프록시를 거쳐 FastAPI에 요청을 전달합니다. 진행 중인 요청은 스트리밍 응답으로 처리 상태를 화면에 전달하고, 비밀 키는 브라우저가 아니라 서버 환경에서 관리합니다. 이 구조는 화면과 검증 로직, 외부 공급자 연결을 각자 맡은 위치에서 처리하도록 나눈 것입니다.

Data 영역은 두 가지 의미로 나눠 보시면 됩니다. 첫째, 한 번의 검증을 진행하면서 단계 사이에 전달되는 주장·출처·근거 상태입니다. 둘째, 사용자가 별도로 저장을 선택했을 때 데이터베이스에 남는 대화와 완료 결과입니다. 검증을 위한 임시 처리 상태가 모두 영구 저장되는 것은 아닙니다.

### 6:30–8:30 | 검증 아키텍처와 5단계

두 번째 그림은 사용자의 요청이 어떤 순서로 처리되는지 보여줍니다. 화면에는 다섯 단계로 정리했습니다.

첫 번째는 입력 분석입니다. 요청에서 검증할 만한 주장을 추출합니다. 현재는 한 요청에서 최대 세 개의 주장을 다룹니다. 두 번째는 출처 검색입니다. 각 주장에 맞는 자료를 찾습니다. 세 번째는 원문 수집입니다. 검색 결과에 나온 설명만 읽는 데 그치지 않고, 확인 가능한 페이지의 본문과 주소를 수집합니다.

네 번째는 주장 검증입니다. 주장과 원문을 대조하고, 인용문이 실제 원문에 있는지, 인용과 출처의 연결이 맞는지 확인합니다. 검증 중 출처 접근 실패나 인용 문제가 재탐색 조건에 해당하면 검색으로 돌아갈 수 있지만, 요청 전체에서 최대 한 번만 수행합니다.

다섯 번째는 결과 정리입니다. 검증된 판정과 인용, 출처를 최종 응답 형식에 맞게 정리합니다. 현재 메인 검증 흐름은 별도의 LLM 개요 합성 단계를 거쳐 답변을 만드는 구조가 아닙니다. 판정과 근거를 검증한 뒤 결과 계약에 맞춰 표시합니다.

일반 대화나 요약 요청은 사실 검증 흐름과 구분해 처리합니다. 그래서 모든 입력을 억지로 주장 추출과 검색에 보내지는 않습니다.

이 다섯 단계는 순서대로 한 번씩만 실행되는 고정 직선은 아닙니다. 검증 단계에서 원문을 확보하지 못했거나 인용을 사용할 수 없는 경우에는 정해진 조건에 따라 검색으로 돌아갈 수 있습니다. 다만 재탐색은 최대 한 번입니다. 횟수를 제한해 끝없이 검색하며 응답이 늘어지는 일을 막고, 그래도 근거가 부족하면 그 상태를 결과에 남깁니다.

각 단계 사이에는 다음 단계가 실제로 필요로 하는 정보가 전달됩니다. 예를 들어 출처 검색에는 검증할 주장과 입력 문맥이 필요하고, 검증에는 주장과 읽은 원문이 필요합니다. 마지막에는 판정과 근거, 출처가 연결되어 있는지 확인합니다. 이렇게 나누면 문제가 생겼을 때 어느 단계에서 자료를 확보하지 못했는지 확인하기도 쉬워집니다.

### 8:30–10:00 | 근거·판정·재탐색

결과를 볼 때는 판정 문구만 보지 않고, 함께 표시된 인용과 출처를 확인하는 것이 중요합니다. 출처가 많다고 해서 근거가 자동으로 강해지는 것은 아닙니다. 여러 페이지가 하나의 자료를 재인용했을 수 있기 때문입니다.

원문을 읽지 못한 자료는 판정 근거로 쓰지 않습니다. 인용이 원문과 맞지 않으면 제외하거나 교정하고, 근거가 여전히 부족하면 판단을 유보합니다. 시스템은 이 조건들을 확인하고, 정해진 경우에만 재탐색을 한 번 수행합니다. 무조건 여러 번 검색해서 답변을 길게 만드는 방식은 아닙니다.

판정과 인용의 연결도 확인합니다. 인용문이 실제로 읽은 페이지에 존재하는지, 인용이 해당 주장과 관련되는지 살핍니다. 출처 주소와 인용이 맞지 않으면 그 인용을 그대로 보여주지 않습니다. 결과에 포함되는 내용은 그럴듯한 문장보다 확인 가능한 연결 관계를 우선합니다.

이제 이 흐름이 화면에서 어떻게 보이는지 시연하겠습니다. 실제 시연 질문은 발표 전에 결과와 출처가 확인된 주제로 고정해 두었습니다. 결과가 도착하면 판정 하나를 선택해 그 판단을 뒷받침한 문장으로 이동하고, 원문과 화면에 표시된 인용을 비교해보겠습니다.

지금 보시는 화면이 True or Not의 검증 시작 화면입니다. 먼저 확인할 주장을 입력하겠습니다.

**[시연 질문 입력: 발표 전에 실제로 확인한 질문으로 교체]**

전송 전에 외부 서비스로 내용을 보내는 데 동의할지 묻는 화면이 나타납니다. 이 동의는 검증 요청을 외부 모델이나 검색 서비스에 전달하기 위한 동의입니다. 대화를 데이터베이스에 저장하는 선택과는 다릅니다. 동의가 확정된 뒤 요청을 보내겠습니다.

#### 10:40–12:00 | 진행 화면

요청을 보냈습니다. 지금 백엔드가 입력을 분석하고 출처를 검색한 다음 원문을 수집하고 있습니다. 진행 상태는 서비스의 검증 단계를 사용자가 알 수 있도록 보여줍니다.

이 과정에서 검색 후보가 발견돼도 곧바로 근거로 확정하지 않습니다. 실제 원문을 읽을 수 있는지 확인하고, 주장에 직접 관계된 내용이 있는지 살펴봅니다. 응답이 처리 중인 동안에는 화면을 보면서 어느 단계인지 설명하겠습니다.

#### 12:00–14:00 | 주장별 결과

결과가 도착했습니다. 먼저 주장별 판정과 설명을 볼 수 있고, 이어서 해당 판정에 연결된 인용과 출처를 확인할 수 있습니다.

이 결과에서 중요한 점은 판정과 근거를 한 화면에서 이어 볼 수 있다는 것입니다. 자료가 확인한 범위와 주장 전체가 같지 않을 수 있으므로 인용이 어떤 문장을 뒷받침하는지 함께 살펴보겠습니다.

**[주장 카드 하나를 선택하고 판정·인용 부분을 가리킵니다.]**

#### 14:00–15:00 | 출처와 원문

이제 출처 링크를 열어 실제 원문으로 이동해 보겠습니다. 결과에 표시된 설명만 믿는 것이 아니라, 사용자가 직접 원문을 확인할 수 있게 연결되어 있습니다.

출처가 열리지 않거나 본문을 확인하지 못했다면 시스템은 그 자료를 검증 근거로 사용하지 않습니다. 이 원칙은 링크가 있다는 사실만으로 자료를 확인했다고 표시하지 않기 위한 것입니다.

#### 15:00–16:00 | 저장 기능과 시연 마무리

대화 저장 기능은 별도 선택입니다. 저장 설정이 꺼져 있으면 검증 결과를 받더라도 대화가 자동 저장되지 않습니다. 저장을 켜고 동의하면 익명 브라우저 세션을 통해 PostgreSQL에 대화를 보관하고 다시 불러올 수 있습니다.

이상으로 입력부터 결과와 출처 확인까지의 시연을 마치겠습니다. 실제 시연이 지연되면 준비한 결과 화면을 사용하되, 합성 예시는 실시간 검증 결과가 아니라는 점을 분명하게 말씀드리겠습니다.

### 16:00–17:30 | 개발 환경과 자동 검증

개발 환경은 Node.js 24와 npm을 권장합니다. 저장소 루트에서 `npm ci`로 프론트엔드 의존성을 설치하고 `npm run dev`로 개발 서버를 실행합니다. 팩트체크를 사용하려면 백엔드도 별도 터미널에서 실행해야 합니다.

프로젝트는 `npm run build`로 프로덕션 빌드를 만들고, `npm run typecheck`와 `npm test`로 타입과 프론트엔드 테스트를 확인할 수 있습니다. GitHub Actions는 프론트엔드 테스트·타입 검사·빌드와 백엔드 잠금 파일 검사·pytest를 수행합니다.

다만 CI에는 실제 모델 키와 DB 주소를 전달하지 않습니다. 따라서 CI가 통과했다는 것은 오프라인 검증이 통과했다는 뜻이지, 실제 모델 응답이나 Render 배포가 성공했다는 뜻은 아닙니다. 실제 공급자 연결과 원격 환경은 별도 QA 기록에서 확인합니다.

이 구분은 발표에서도 중요합니다. 자동화 검사는 코드의 타입과 테스트, 빌드처럼 반복 가능한 항목을 빠르게 확인합니다. 반면 외부 검색 결과의 품질이나 특정 페이지의 접근 가능 여부는 실제 외부 환경에 영향을 받습니다. 따라서 코드 검사 통과를 실제 서비스 전체의 품질 보증으로 과장하지 않고, 확인한 범위를 함께 기록합니다.

### 17:30–18:45 | 대화 저장과 개인정보 경계

대화 저장은 기본 꺼짐입니다. 저장을 사용하려면 사용자가 별도의 선택을 확정해야 하며, 선택한 뒤에 저장되는 메시지가 대상입니다. 프론트엔드가 DB에 직접 접근하지 않고 FastAPI를 통해 저장과 조회를 요청합니다.

대화 소유권은 익명 브라우저 세션으로 확인합니다. 쿠키를 지우거나 만료하면 이전 대화에 다시 접근하지 못할 수 있습니다. 저장 동의를 해제하는 것과 기존 대화를 삭제하는 것도 같은 동작이 아닙니다. 보관과 삭제에 관한 자세한 동작은 백엔드 안내와 실행 기록에 정리되어 있습니다.

저장 데이터도 필요한 범위로 제한합니다. 완료된 검증 결과를 복원할 때 필요한 입력, 주장, 판정, 인용, 출처 등의 정보를 저장하고, 수집한 페이지 전체 본문이나 모델의 원시 응답, 비밀값은 저장 대상에서 제외합니다. 저장 기능을 소개할 때는 사용자가 무엇에 동의하는지와 어떤 정보가 남는지를 구분해 설명하는 것이 중요합니다.

### 18:45–19:30 | 배포와 현재 확인 범위

프론트엔드는 Vercel에 배포되어 있고, Render 설정은 백엔드와 PostgreSQL을 구성하도록 관리합니다. 배포가 구성되어 있다는 사실과 원격 환경의 모든 기능이 검증됐다는 사실은 구분해야 합니다.

현재 연결 상태나 배포 검증 여부는 README에서 안내하는 배포 문서와 QA 실행 기록을 기준으로 확인합니다. 발표에서는 확인된 결과만 말씀드리고, 아직 확인하지 않은 부분은 완료됐다고 표현하지 않겠습니다.

이렇게 배포 환경과 개발 환경의 확인 결과를 구분하면, 시연 중 외부 서비스 문제나 네트워크 지연이 생겨도 어디까지가 제품 동작이고 어디서부터가 운영 환경 문제인지 설명할 수 있습니다. 배포 주소가 있다는 사실만으로 모든 입력에서 항상 같은 응답 시간을 보장하지는 않습니다.

### 19:30–20:00 | 마무리

정리하면 True or Not은 온라인 주장을 원문과 대조하고, 판정뿐 아니라 근거와 불확실성도 함께 보여주는 서비스입니다.

사용자가 출처를 따라가며 직접 확인할 수 있게 만드는 것이 저희의 목표입니다. 이상으로 발표를 마치겠습니다. 들어주셔서 감사합니다.

## 시연 지연 시 진행 요령

실제 응답이 늦어지면 진행 화면을 보여주면서 입력 분석·검색·원문 수집·검증 단계를 설명합니다. 준비한 화면으로 전환할 경우에는 **사전 준비한 예시**라고 밝히고, 이를 실시간 요청의 결과처럼 소개하지 않습니다. 일정 시간 안에 응답이 없으면 오류 문구와 함께 현재 확인 범위를 설명하고 시연을 마무리합니다.
