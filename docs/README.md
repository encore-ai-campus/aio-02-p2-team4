# True or Not 문서 안내

기준일: 2026-10-15. 현재 코드와 날짜별 실행 기록을 기준으로 문서를 관리한다. 배포 구성은 Vercel 프런트·프록시와 Render 백엔드·PostgreSQL이며 실제 확인 범위는 [배포](배포.md)와 [QA 실행기록](qa/실행기록/)에서 구분한다. 최신 에이전트 변경과 대화 만료 정책은 [아키텍처](아키텍처.md)와 [Agent 작업현황](agent/agent_작업현황.md)을 따른다.

## 읽는 순서

| 알고 싶은 내용 | 기준 문서 |
|---|---|
| 어떤 제품이고 무엇을 제공하는가 | [기획서](기획서.md) |
| 현재 코드가 어떻게 동작하는가 | [아키텍처](아키텍처.md) |
| 무엇이 끝났고 다음에 무엇을 해야 하는가 | [작업현황](작업현황.md) |
| Render에 어떻게 배포하고 확인하는가 | [배포](배포.md) |
| 무엇으로 검증하며 어떤 결과가 기록되어 있는가 | [QA 검증기준](qa/검증기준.md), [실행기록](qa/실행기록/) |

제품은 입력한 주장을 원문 근거와 연결해 확인된 내용과 판단의 한계를 함께 보여주는 검증 도구다. 먼저 기획서로 범위를 읽고, 작업현황의 미결정 사항과 우선 작업을 확인한다.

## 문서 관리 규칙

1. 제품 목적·범위·확정 정책은 기획서에만 관리한다. 미결정 정책은 작업현황의 D 표에 둔다.
2. 모델·API·계약·제한·처리 흐름은 아키텍처에 관리한다. 전체 필드의 기준은 연결된 소스 코드다.
3. 완료·남은 작업은 작업현황의 T 표 하나로 관리한다. 상태는 구현, 검증, 실제 배포를 구분한다.
4. 테스트 수·관측 결과는 날짜별 QA 실행기록에만 적는다. 과거 결과를 최신 실행으로 표시하지 않는다.
5. 정책과 코드가 다르면 작업현황에 차이를 기록한다. 제안은 결정 완료로 바꾸지 않는다.
6. 과거 기록은 [archive 안내](archive/README.md)에 보존한다. archive의 계획·상태·명령은 현행 지침이 아니다.

모든 현행 문서는 기준일과 역할을 표시한다. 작업 번호는 T, 결정 번호는 D로 관리하며 이전 L·FR·R·C 번호는 작업현황의 참고 열로 추적한다.
